
# Vault Initialization and Configuration (`vault-init`)

This repository provides scripts, configurations, and instructions to initialize and configure a HashiCorp Vault instance. It includes policies, AppRoles, unseal workflows, and containerized initialization for automated environments.

## Overview

`vault-init` is a set of scripts and configuration files that automate:

1. **Launching a Vault container** (with a `file` backend for storage).
2. **Unsealing Vault** using the provided unseal keys.
3. **Applying policies** (e.g., `issuer1-policy.hcl`, `issuer2-policy.hcl`, etc.).
4. **Creating AppRoles** and capturing `ROLE_ID`/`SECRET_ID` pairs into an environment file or displaying them on screen.
5. **Optionally** storing credentials in a Docker volume so that the Vault container can persist across restarts.

---

## Repository Structure

- **`config.hcl`**  
  Main Vault server configuration (UI, listener, `file` storage).

- **`issuer*-policy.hcl`**  
  Example Vault policies that define permissions on specific paths (e.g., `transit/*`).

- **`credentials/`**  
  - `unseal-keys.txt`: Contains Vault unseal keys (never share this publicly).
  - `root-token.txt`: Contains the Vault root token (also very sensitive).

- **`env/`**  
  - `vault_approle.env`: An environment file generated by `vault-init.sh` with the `ROLE_ID` and `SECRET_ID` for each AppRole.

- **`vault-init.sh`, `vault-init-windows.sh`**  
  Scripts that perform the unseal process, apply policies, create AppRoles, and output or save the necessary IDs.

- **`Dockerfile.vault-init`**  
  Dockerfile that builds a Vault CLI environment (Ubuntu + Vault) for running initialization scripts.

- **`setup_all.sh`, `setup_all_windows.sh`**  
  Scripts that:
  1. Create a Docker network and volume.
  2. Launch the Vault container.
  3. Build the `vault-init` Docker image.
  4. Run a `vault-init-container` with the unseal keys and policies mounted.
  5. Execute `vault-init.sh` or `vault-init-windows.sh` inside that container.

- **`vault-data/`**  
  This folder simulates the Vault `storage` on disk. It contains the internal Vault data (tokens, keys, policies, etc.). **Sensitive** and typically not for public repos.

- **`Instrucciones.txt`**, **`README.md`**, etc.  
  Additional documentation and instructions.

## Requirements

1. **Docker** and optionally **Docker Compose**.
2. A **Bash shell** (or a Windows environment that can run `.sh` scripts, using WSL or Git Bash).
3. An **internet connection** (Docker pulls images).
4. [**Vault CLI** (optional)**] if you want to manually interact with Vault outside the container.

## Installation

1. **Clone** this repository:
   ```bash
   git clone <repository-url>
   cd vault-init
   ```
2. **Check** the contents of:
   - `setup_all.sh` (or `setup_all_windows.sh` on Windows)
   - `vault-init.sh` or `vault-init-windows.sh`
   - `config.hcl`
   
   Adjust variables if necessary (e.g., Docker network name, volume name).

## Configuration

### Vault Configuration (`config.hcl`)

- **Listener** on `0.0.0.0:8200` with TLS disabled (development).  
- **Storage** set to `file` (path `/vault/file`).  
- `api_addr` and `cluster_addr` set to local addresses.

```hcl
ui = true

listener "tcp" {
  address     = "0.0.0.0:8200"
  tls_disable = true
}

storage "file" {
  path = "/vault/file"
}

disable_mlock = true

api_addr = "http://127.0.0.1:8200"
cluster_addr = "https://127.0.0.1:8201"
```

### Policies

- `issuer1-policy.hcl`, `issuer2-policy.hcl`, `issuer3-policy.hcl`  
  Each policy grants certain capabilities on paths like `transit/*`.

Example:
```hcl
path "transit/*" {
  capabilities = ["create", "read", "update", "delete", "list"]
}
```

## Usage

### 1. Run the main setup script

On Linux/macOS:
```bash
./setup_all.sh
```
On Windows (Git Bash / PowerShell):
```bash
./setup_all_windows.sh
```
This script will:
1. Create a Docker network (`my_network`) if not present.
2. Create a Docker volume (`vault-data-new`).
3. Spin up a temporary container to copy `vault-data/` into that volume and set permissions.
4. Launch the main Vault container using `hashicorp/vault`.
5. Build an image named `vault-init-image` from the `Dockerfile.vault-init`.
6. Start a container called `vault-init-container` with necessary credentials/policies mounted.
7. Execute `vault-init.sh` or `vault-init-windows.sh` inside that container.

### 2. Watch the logs or console output

- The script will wait a few seconds for Vault to start, then:
  - Unseal Vault using the first 3 unseal keys in `credentials/unseal-keys.txt`.
  - Login with the root token from `credentials/root-token.txt`.
  - Apply the `.hcl` policies (e.g., `issuer1-policy.hcl`).
  - Create roles in `auth/approle/`.
  - Output (or store) each `ROLE_ID` and `SECRET_ID`.

### 3. Retrieve the AppRole credentials

- If using the default `vault-init.sh`, check the file `env/vault_approle.env` created by the script.
- If using `vault-init-windows.sh`, the credentials are printed on-screen.

Example file:
```
# Variables AppRole
ROLE_ID_ISSUER1=...
SECRET_ID_ISSUER1=...
ROLE_ID_ISSUER2=...
SECRET_ID_ISSUER2=...
ROLE_ID_ISSUER3=...
SECRET_ID_ISSUER3=...
```

### 4. Interact with Vault

- Vault is now unsealed and has policies/roles set.  
- You can use `ROLE_ID` and `SECRET_ID` to login programmatically via `auth/approle/login`.

## Additional Notes

1. **Security**  
   - `unseal-keys.txt` and `root-token.txt` are extremely sensitive.  
   - `vault-data/` contains internal Vault data. Do not share publicly.

2. **Production Considerations**  
   - Use TLS (`tls_disable=false`), do not expose `unseal-keys.txt` in the repo, and consider storing secrets in a secure environment variable management system.
   - Possibly use `raft` or `consul` storage instead of `file`.

3. **Windows vs Linux Scripts**  
   - `setup_all_windows.sh` and `vault-init-windows.sh` are adapted for Windows, typically printing the AppRole credentials to console rather than writing an `.env` file.

4. **Customizing**  
   - Edit `issuer*-policy.hcl` for your own paths and capabilities.  
   - Adjust the Docker commands in `setup_all.sh` (network names, container names, volumes) as needed.
